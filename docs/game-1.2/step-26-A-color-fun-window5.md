## 一、开工前的现状审查（先看清楚再动手）

对着 `src/games/color-fun/`（`levels.ts` 517 行 / `index.ts` 423 行 / `guide.ts` 118 行 / `levels.test.ts` / `levels188.test.ts`）逐条核对，结论如下。

### 1. 线稿够不够铺 188 关

规格里写的「六幅线稿」已经过期：1.1 追加四个村镇时同时补了四张，现在是 **10 幅**，`PICTURES[ci]` 与章节一一对应。
问题不在总数而在**每章只有一幅**：后四章分别是 22 / 22 / 23 / 22 关，也就是同一张画连着看二十多遍。
第 10 章「限色挑战场」的「彩虹热气球」9 块，一路重复到第 188 关，重复感最强。

### 2. 调色锅的混色算法

`MIX_TABLE` 是**按名字查表**，不是 RGB 平均：

```
红色+黄色→橙色  蓝色+黄色→绿色  红色+蓝色→紫色
红色+红色→深红  黄色+黄色→金黄  蓝色+蓝色→深蓝
```

「红 + 黄 = 橙」这类结论本身是对的（查表查出来的，不是算出来的）。真正的缺口是**表太小**：
只有 6 条，没有白、没有黑，调不出「浅」和「深」，倒进两种非原色就一句「调不出新颜色」。

### 3. 明暗渐变章（第 7 章）的深浅判定

**根本没用亮度**：靠 `SHADE_LADDERS` 七条手写数组的下标顺序，`index.ts` 再按 `cfg.tasks` 的数组顺序卡「下一块该涂谁」。
把七条阶梯的 CIE L\* 算出来，两条不合格：

| 阶梯 | L\* | 相邻级差 |
| --- | --- | --- |
| 浅绿 > 绿色 > 深绿 | 94.6 / 85.1 / 57.5 | **9.5** / 27.6 |
| 浅黄 > 黄色 > 金黄 | 95.6 / 89.6 / 76.9 | **6.0** / 12.7 |

浅黄和黄色差 6%，孩子肉眼分不出「哪个更浅」，却要按顺序涂——这是本款目前最硬的一处教学错误。

### 4. 互补配色表

`COMPLEMENT` 是 红↔绿、蓝↔橙、黄↔紫，**对**（颜料 RYB 色环，正是给孩子讲的那一套）。
`ANALOGOUS_NEXT` 红→橙→黄→绿→蓝→紫→红 也成环，对。

### 5. 限色章的调色次数上限有没有解

`budget = needMix.length + (t > 0.5 ? 1 : 2)`，而 `needMix` 里每种颜色都恰好一次开锅就能调出来，
所以**一定有解且有富余**。但这是「凑巧成立」：既有用例只断言 `budget > needMix.length`，
**没有任何搜索去证明「这些颜色真的调得出来」**。一旦以后往 `needMix` 里塞一个两步才能调出的颜色，测试照样绿。

### 6. 填色方式与撤销

点一块填一整块（`onRegion`），**没有撤销**。涂错要扣一颗爱心，扣满 `maxWrong + 1` 直接 `ctx.lose`。
「涂色会失败」这件事本身就和这一款的定位拧着。

### 7. 完成的画能不能存

**不能**。关卡一结束 DOM 就拆掉，画过什么都不留。

### 8. `guide.ts` 有没有泄题

**没有**。十章条目全是方法（先读完指令、由浅到深、先统计要几种混合色…），一关的具体配色一个字都没写。

## 二、这一步要做的事

### 1. 混色改成「减色法查表 + 受控插值」（硬性）

- 新建 `mix.ts`，颜料表写死，**结果由查表给出，颜色值取颜料自己的 hex，不做 RGB 平均**。
  留一个 `naiveRgbAverage()` 只为在用例里把「RGB 平均下蓝 + 黄 = 灰」这条错误结论钉死当反例。
- 配方补齐三类：三原色两两 → 间色；任意色 + 白 → 浅；任意色 + 黑 → 深；白 + 黑 → 灰。
  1.0 的「同色再倒一勺 → 更浓」（红+红=深红）保留，它是前 99 关的既有配方，动不得。
- `MIX_TABLE` 保持 `"甲+乙" → 结果名` 的老形状对外导出（`scripts/smoke188.mjs` 直接读它），
  但改由结构化配方生成；**同一结果有多条配方时，把只用三原色的那条排在最后**，
  这样冒烟脚本按插入序取到的仍然是三原色配方，前 99 关的自动化跑法一行都不用改。
- 「受控插值」用在搅拌动画上：锅里两色先按乘法（减色）混，再朝查表结果收敛，
  所以看得见蓝加黄一路走向绿，而不是先变灰再跳成绿。

### 2. `validateLevel()` 跑遍 188 关（硬性）

新建 `validate.ts`，对每一关查三件事：

1. **可解性**：以「手里有哪些颜色」为状态做 BFS，每开一次锅从 `potInputs` 里取两样倒，
   受 `budget` 约束，搜不到目标色就是不可解；
2. **区域覆盖**：每个任务区域都在线稿里、不重复，并且按玩法都有对应的指令 / 编号 / 图例符号 / 规则；
3. **可分辨**：同一关的目标色两两 CIE76 ΔE ≥ 16；渐变关额外要求同阶梯相邻两级 L\* 差 ≥ 12。

用例跑全量 188 关，**有一关不过就回去修数据**。

### 3. 调色板数据修正（第 3 条查出来的错）

只动 1.1 追加的 `SHADE_PAINTS` / `SHADE_LADDERS`，**不碰前 99 关也在用的基础色 hex**：

| 阶梯 | 改成 | 相邻级差 |
| --- | --- | --- |
| 绿 | 浅绿 > **中绿 `#51cf66`（新）** > 深绿 | 20.1 / 16.9 |
| 黄 | 浅黄 > 金黄 > **深黄 `#9d7604`（新）** | 18.7 / 24.9 |
| 粉 | **浅粉 `#ffd6e6`** > 粉色 > 深粉 | 13.3 / 20.9 |
| 蓝 | **浅蓝 `#c5e4ff`** > 蓝色 > 深蓝 | 14.1 / 28.0 |
| 橙 | **浅橙 `#ffe3c2`** > 橙色 > 深橙 | 15.6 / 19.8 |

粉 / 蓝 / 橙三条的浅色顺手加深了一点：原来的浅色与白画布只差 ΔE 16 上下，涂上去看不出涂过。

浅色互相之间天生就近（浅粉/浅红 12.5、浅黄/浅橙 12.8），**靠调整 hex 是解不掉的**，
所以渐变关改成「先算一张阶梯相容表，同一关只挑 ΔE ≥ 16 的两条阶梯」，21 对里有 17 对可用，够排 22 关。

### 4. 线稿扩到 16 幅

新增 6 幅全手写内联 SVG，全部原创造型：小船 / 蝴蝶 / 城堡 / 火箭 / 大树 / 小猫，区域数从 9 到 16 递增。

### 4. 真机冒烟揪出来的两处「点不着」

单测全绿之后跑 `SMOKE_ONLY=color-fun node scripts/smoke188.mjs`（375×667 真浏览器），第 140 / 188 关直接挂在
「第 csky 块被完全盖住了，点不到」。查下来是两个各自独立的界面缺陷，单测看不出来：

- **手机上画布会被顶出屏幕**。标题栏加关卡条先吃掉三成屏高，画布再占 55%，一屏就装不下，
  底下的调色盘必须滑出来点——一滑画就没影了，选完颜色还得滑回去找要涂的那一块。
  本该交给 `position:sticky`，但壳层的滚动区是 `overflow:hidden`，浏览器不拿它当粘性定位的参照物（实测画照样滑走），
  所以 `ui.ts` 里的 `pinCanvas()` 自己按滚动量把画布钉在滚动区顶上，跟到整块下沿为止；顺手给指令区加了 84px 天花板。
- **画室里换不了线稿**。`.clf-sheet` 是竖着的弹性盒，装不下时子项会被压缩，线稿那一排被压成 **4px 高**，
  按钮整个漏在框外，真手指点下去全落空（用脚本直接 `.click()` 反而是好的，所以单测发现不了）。
  改成 `.clf-sheet>*{flex:0 0 auto}`，装不下就让画室自己滚。

两处都补了回归用例（`pinCanvas` 的钉位与拆监听、画室子项不许收缩）。

### 5. 前 99 关没被碰过，怎么证

三道锁，缺一不可：

1. **逐关指纹**：`upgrade12.test.ts` 把 `buildLevel(0..98)` 的输出按稳定序列化后算 SHA-256，
   与升级前的 `80ba44ff8576dad5…` 逐字节比对，钉死在用例里。
2. **形状断言**：前 99 关的 `pic` 一律 < 6（新线稿全排在数组末尾）、模式只在 1.0 那四种里、
   不出现 1.2 新加的任何字段（`potInputs` / `orderGroups` / `legend`）。
3. **真机通关**：第 1 / 31 / 61 / 99 关在 360×640 真浏览器里逐关点通，零 console 报错；
   `scripts/smoke188.mjs` 的老存档兼容四项也全过（99 长度的老存档读出来补到 188，前 99 关星级原样）。
