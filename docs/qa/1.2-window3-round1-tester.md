### 0.2 取证手段（两层，缺一不可）

光跑 `vitest` 只能证明「模块函数对」，证明不了「从首页点进去能玩到胜负」。所以分两层：

**A 层 · 真实浏览器**（Chrome 148 headless + `puppeteer-core`，跑在 `vite preview` 产物上）

工具：`scripts/qa-window3/`（测试员自建的走查驱动，不属于玩法代码，只读页面 + 发输入事件）。

每款走这条链路：

1. 打开首页 `/`，在首页卡片列表里**按标题找到这一款并点进去**（不是直接改 hash），记录卡片是否存在；
2. 等挂载，抓 `pageerror` / `console.error`；
3. 读模式条，列出这一款真正提供了哪几个模式入口，与 `meta.modes` 对账；
4. 每个模式都进一次，用「键盘扫键 + 舞台网格指针」驱动，等结算面板（`.overlay`）出现，
   记录结算文案是「赢」还是「鼓励」——**赢一次输一次都要拿到**；
5. 有战役的把 `yiduo-yixing.l99.<id>` 预置成全 3 星解锁，分别点开第 **1 / 100 / 188** 关，
   确认关卡真的挂载起来（`.l99-stage` 有内容）而不是空白；
6. 退出回首页 → 再进一次，确认 `destroy` 之后重挂不报错（顺带看 rAF / timer 有没有炸）；
7. 视口切 **360×720** 再走一遍主链路，量 `scrollWidth - clientWidth` 的横向溢出像素。

**B 层 · 纯逻辑模拟**（Node + `tsx`/vitest 直接 import 游戏自己的逻辑模块）

A 层的胜负是「随机输入撞出来的」，撞不到不等于没有。所以对每一款再补一次确定性模拟：
调这一款自己的 `logic.ts` / `match.ts` / `arena.ts` / `endless.ts` 等纯逻辑导出，
用固定策略把一局跑到 `win` 和跑到 `lose`，无尽跑够波次看能不能持续。
这一层的好处是可复现、可量化（回合数、波次、分数）。
