### 1.3 菜鸟→地狱 固定 seed 相邻档对下，胜率单调 —— **❌ 阻断**

口径：15×15，中心先落一颗黑子，之后两档轮流走；每对相邻档**强档执黑执白各一半**，
固定 seed（mulberry32），一局跑到五连或棋盘下满。

先跑 12 局/对：

| 相邻档对 | 强档胜 | 弱档胜 | 和 |
| --- | --- | --- | --- |
| novice → easy | 12 | 0 | 0 |
| easy → normal | 11 | 1 | 0 |
| **normal → smart** | **4** | **7** | 1 |
| smart → master | 12 | 0 | 0 |
| **master → hell** | **6** | **6** | 0 |

怀疑是 seed 噪声，加到 **每对 40 局 × 3 个 seed 基点 = 120 局**复核，结论没变：

```
novice → easy    120 局: 强档胜 120 负  0 和  0 (100.0%)   40-0-0   40-0-0   40-0-0
easy   → normal  120 局: 强档胜 114 负  6 和  0 ( 95.0%)   36-4-0   39-1-0   39-1-0
normal → smart   120 局: 强档胜  36 负 54 和 30 ( 30.0%)   13-16-11 12-20-8  11-18-11   ← 倒挂
smart  → master  120 局: 强档胜 120 负  0 和  0 (100.0%)   40-0-0   40-0-0   40-0-0
master → hell    120 局: 强档胜  60 负 60 和  0 ( 50.0%)   20-20-0  20-20-0  20-20-0    ← 精确打平
```

- `smart` 对 `normal` 的胜率只有 **30%**（36/120），是明确的**强弱倒挂**；
- `hell` 对 `master` **每个 seed 都精确 20-20-0**，这种整齐得反常的分布本身就是线索。

跨档对照是正常的：`hell` vs `novice` = **6/6 全胜**，说明对局框架本身没问题。

### 1.3.1 根因：`hell` 与 `master` 在实战里走的是**同一步棋**

拿 60 个由 `normal` 自对弈铺出来的真实中盘局面，同一局面、同一 rng，逐档比对着法：

| 相邻档对 | 着法相同 | 说明 |
| --- | --- | --- |
| novice vs easy | 2/60（3.3%） | 正常，两档差别大 |
| easy vs normal | 22/60（36.7%） | 正常 |
| normal vs smart | **51/60（85.0%）** | smart 大部分时候在抄 normal，剩下 15% 的差异反而下成了软棋 |
| smart vs master | 36/60（60.0%） | 正常 |
| **master vs hell** | **60/60（100.0%）** | **一步不差，完全一致** |

`master` 与 `hell` 100% 同步，正好解释了 60:60 与每个 seed 20-20-0：
两档在每一局里都下出同样的棋，胜负就只由**先手优势**决定 ——
强档执黑赢 20 局、执白输 20 局，加起来恰好打平。

顺着代码看，`hellMove`（`ai.ts:1071-1117`）有两道口子把结果交回给 `masterMove`：

```
ai.ts:1096-1099   对手有活四 / 双三 / 连续冲四 → 直接 return masterMove(...)
ai.ts:1104-1116   平静局面 → 先取 masterMove 当 fallback,
                  深搜只有在 found.score >= preferScore + SEARCH_OVERRIDE_MARGIN 时才敢改
                  （SEARCH_OVERRIDE_MARGIN = 4000,见 ai.ts:757）
```

实测 143 个真实中盘局面的分支落点：

```
立即成五 / 挡五        :   8 (5.6%)    ← 六档都一样
自己有 VCF 连续冲四     :   3 (2.1%)
直接转 masterMove       :  30 (21.0%)   ← ai.ts:1096-1099
平静局面(才轮到深搜)    : 102 (71.3%)   ← ai.ts:1104-1116
```

也就是说：21% 的局面 `hell` **压根不搜索**，直接交给 `master`；
剩下 71% 虽然走到了深搜，但 4000 分的 override 门槛在这 60 个局面里**一次都没跨过**，
最终仍然原样返回 `masterMove` 的答案。两条路加起来 ≈ 100%，`hell` 在默认规则下
（`opts.forbidden` 不开时，`ai.ts:1088-1091` 的抓禁手分支也进不去）**退化成了 `master`**。

补充旁证 —— 解局考卷（120 道解局，看各档能不能找出保持必胜的首着）：

```
novice=1/120  easy=76/120  normal=105/120  smart=105/120  master=110/120  hell=110/120
                                            ^^^^^^^^^^^^^ 与 normal 持平    ^^^^^^^^^^^^ 与 master 持平
```

**两把互相独立的尺（实盘胜负 / 解局考卷）指向同一个结论**：
`smart` 没有强过 `normal`，`hell` 没有强过 `master`。

**为什么仓库自带的用例没红：**

1. `tiers.test.ts` 的「能力单调」基本功电池只有 5 道题，且断言
   `for (const s of scores.slice(2)) expect(s.score).toBe(DRILL_TOTAL)` ——
   即 `normal` / `smart` / `master` / `hell` 一律满分，这把尺**从 normal 起就饱和了**，
   分不出上面四档。
2. 「实战单调」四条用例挑的是 easy→novice、normal→easy、master→**easy**、hell→**normal**，
   **恰好跳过了 normal↔smart 与 master↔hell 这两对相邻档**。

所以现有测试与「相邻档单调」这条点名要求之间存在真实缺口，不是测试写法差异。

**建议（给开发，不在本轮修）**：

1. `hell`：把 `SEARCH_OVERRIDE_MARGIN`（现为 4000）调到深搜真的能改写 `master` 答案的量级，
   或者让 `ai.ts:1096` 那条「对手有威胁就转 master」的捷径也先过一遍深搜；
   否则不开禁手规则时 `hell` 与 `master` 就是同一档。
2. `smart`：`normal` 已经会成五 / 挡五 / 走活三，`smartMove` 那两层搜索反而把好棋换成软棋
   （85% 抄 normal，剩下 15% 下输），需要重新校准它的评估。
3. `tiers.test.ts`：把实战用例补成 **5 对相邻档全覆盖**，并把「能力单调」电池换成更难的考卷
   （本报告第 1.3.1 节用的解局考卷可以直接复用），让这条线以后红得出来。

- 补位的新块从棋盘外 **-3.00** 行往里落（16 帧），落到 0.00 才归位；
