## 六、走查工具本轮纠出的三处偏差（关系到前两轮结论的可信度）

测试员的取证工具本身也会骗人。本轮抓到三处，都已修并重跑：

1. **自带地图的两款点不开关卡（影响 `candy-swing`）。** `openCustomLevel` 用的是合成 `el.click()`，而 `candy-swing` 的关卡格子只吃真实 pointer 事件——**点了没反应，驱动却按「进去了」记账**。更糟的是走查流程会先点「🗺️ 闯关 188 关」，而这一款首屏本来就是关卡格子、那个按钮是「直接开打」，**先点它反而会跳进别的关**。也就是说**前两轮 `candy-swing` 的战役关号是不可信的**（进的不一定是目标关）。现改为真鼠标点击 + 这类款不再先点「闯关」，并加了「地图还看得见就不算进关」的兜底。修好后补测：第 188 关赢、第 1/60/133 关 15 秒随机输入没分胜负、360px 零溢出、最小热区 44px、console 零报错。
2. **`bowling-lane` 那条「360px 关卡页溢出 24px」是误判（S1 撤回，见 §7）。**
3. **`prince-princess` 摆烂扫描扫错了模式**（扫的是双人，漏了单人），因此第 2 轮把这一款判成「干净」。这一条直接导致漏掉了本轮的 B2。

工具改动都在 `scripts/qa-window3/` 下，`src/` 一行没碰。

### 为什么这三条是阻断而不是严重

「一朵一星」的核心是**一关一颗星**——星星是孩子努力的凭证。现在这一窗有 **`sky-squad` 180 关 + `prince-princess` 110 关 + `duo-vs-star` 72 关 + `bumper-cars` 31 关，合计约 393 个关卡实例，把手机放桌上不管就能拿星，其中绝大多数还是三星**。`duo-vs-star` 第 157 关**开局 1 秒**就弹「★★★ 过关！一次都没被撞出去，太稳啦！」。这不是难度偏低，是**奖励与付出彻底脱钩**，产品最核心的那条承诺当场作废。四款里有三款的**第 1 关**就在名单上——新玩家第一次点进去，什么都不做就通关了。

四条的根因还各不相同，不能指望一处改动一起解决：

- `sky-squad`：判罚链路是死代码（`escaped` 恒为空）；
- `prince-princess`：AI 搭档强度盖过了玩家的存在感；
- `duo-vs-star`：`star-lift` / `night-hops` 两张场地的边界跟 AI 走位对不上，对手自己掉下去；
- `bumper-cars`：AI 对手自己冲下悬崖。

### 交接清单（按处理顺序）

1. **B1 `sky-squad`** — `stepFoes` 两行错位，改动量最小、收益最大，建议第一个修。
2. **B3 `duo-vs-star`** — 先看 `star-lift` / `night-hops` 两张台子的 `bounds` 与 AI 走位，19/19 和 16/19 这种集中度基本能定位到场地。
3. **B2 `prince-princess`** — 需要产品一起定：单人模式的 AI 搭档该多强？这条不是纯技术修复。
4. **S5 `bumper-cars`** — 顺带把「撞飞 1 台对手车」这句错误归因的结算文案一起改了。
5. **O1 `candy-swing`** — 请先回答「`sim.ts` 和真机是不是同一套物理」，再决定那 12 关要不要动。
6. **M1 / M2 / M4 / M5 / M6 / M7 / M8 / M9** — 轻微项，可与发布并行处理。

## B.3 【订正一】S1 撤回是对的，但撤回的**理由**不对——真凶是首页搜索框的 ✖ 按钮

正文 §7 撤回 S1 时写的理由是：溢出元素「全在 `nav.tabs.cat-tabs` / `nav.tabs.mode-chips`
这两条 `overflow-x:auto` 的横滑条里」。**这一句量错了。** 那两条横滑条恰恰是被接住的那一批。

我把「谁真的撑宽了文档」这个判据写死成程序（`scripts/qa-window3/homeoverflow.mjs`）：
从元素往上走祖先链，只要有一个祖先是 `overflow-x: auto / scroll / hidden`，
超出的部分就被它吃掉、撑不宽 `html.scrollWidth`；**一路到 `body` 都是 `visible` 的才算数**。
360px 首页实测：

| 元素 | 超出视口 | 祖先链上有人接住吗 |
| --- | --- | --- |
| **`.home-search`** | **24px**（left=14、宽 370） | **没有**，一路 `visible` → **就是它撑宽的** |
| `.home-search-clear` | 15px（它在 `.home-search` 里面） | 没有 |
| `.tab`「🎨动手」 | 389px | **有**：`nav.tabs.cat-tabs{overflow-x:auto}`，右边只到 346px，**不撑宽文档** |

再往下追一层：`.home-toolbar` 宽 **331px**，里面唯一的孩子 `.home-search` 却排到 **370px**，
硬顶出去 39px。为什么顶得出去——**因为搜索框右边那个「✖ 清空」按钮在搜索框是空的时候也没被藏住**：

```
.home-search-clear{display:grid;place-items:center;min-width:44px;min-height:44px;margin-right:-10px; ...}
```

`src/ui/home.ts` 的代码是写了 `clearBtn.hidden = true` 的（第 299 行，第 602 行也跟着 query 收放），
但**作者样式表里的 `display:grid` 会盖掉浏览器 UA 的 `[hidden]{display:none}`**
（作者样式的优先级本来就高于 UA 样式），所以 `hidden` 属性形同虚设。实测：

```
.home-search-clear:代码里 hidden=true,但算出来 display=grid、宽 44px、右边到 375px
```

因果验证（只在浏览器内存里临时改内联样式，不碰产品代码）：

```
把 .home-search-clear 临时 display:none → .home-search 370px → 331px,文档溢出 24px → 0px
```

**一改就归零，因果链闭合。** 所以这 24px 从头到尾跟 `bowling-lane`、跟本窗 19 款都没有关系，
是首页 `src/ui/home.ts` 里 `HOME_EXTRA_CSS` 的 `.home-search-clear` 缺一条
`&[hidden]{display:none}`（或者把 `hidden` 换成加 class）。

顺带带出两条正文没记的、**玩家真能碰到**的后果：

1. **空搜索框上永远挂着一个「✖」**。孩子还没输入任何东西，右边就有一个「清空」按钮，
   点它没有任何效果——这是个一直在的多余控件，不是溢出问题。
2. **这个 ✖ 在 360px 上有 15px 被裁在屏幕外**（它右边到 375px，视口 360px），
   而 `html{overflow-x:hidden}` 又让人划不过去。它自己写着 `min-width:44px`（本来是达标的热区），
   **实际能点到的只剩 29px**——等于首页上还有一处 M1 类的热区不达标，只是前几轮量的是
   `.game-stage` 里面，没量到首页。

**定级：轻微。** 归属**不在本窗 19 款**——`src/ui/**` 是别的窗口的地界，
本窗修复员按分工也不许碰。**建议交主管转给首页那一窗**，改动只有一行 CSS。
证据 `docs/qa/_evidence/window3-round3-homeoverflow.json`。

## B.4 【订正二】B2 / B3 的根因：不是「练习关门槛低」，也不是「AI 队友替你打」

派发单让我核一条：`prince-princess` 第 1 关会不会是**练习关设计如此**——
`doorOpen()` 在 `enemyTotal === 0` 时 `killRatio` 直接算 1，门一开始就是开的。
**实测下来这个假设不成立。** `buildLevel(0)` 的真实参数是：

```
第 1 关「樱花城堡·城门前」teach=true noRisk=true requiredRatio=0.5
enemies=3 gems=7 gemGoal=4 goalNeedsAll=false timeLimit=0 len=1780 goalX=1650
```

`enemyTotal = 3`（不是 0），`requiredRatio = 0.5`，所以**必须真打倒 2 只怪门才开**，
`killRatio=1` 那条捷径根本没被走到。而摆烂那一局的结算原文是
「**路上的怪一只不剩**、只用了 12 秒、宝石收了 5 颗」——3 只全打倒了、宝石也超了目标 4 颗。
打的人是谁？是 `index.ts` 第 1304–1306 行：

```ts
// 单人模式:没被操作的那位交给小伙伴 AI 托管
const feed: Input[] = world.heroes.map((_, i) => {
  if (opts.players === 2 || i === world.active) return inputs[i] ?? emptyInput();
  return botInput(world, i, dt);
});
```

**单人模式下你只操作一位英雄，另一位全程由 `botInput` 托管**，而 `goalNeedsAll = false`
——只要有一位走到城门就通关。于是「玩家不动」≠「场上没人动」，搭档一个人就把关打完了。
按这个真机模型重扫全 188 关：**110 关自动过关、其中 94 关三星**（正文引的就是这一组数）。

**所以 B2 的定性是「阻断」而不是「设计如此」**：练习关放宽门槛是有的（`noRisk=true`、不限时），
但门槛并没有被绕过，是**托管 AI 的强度盖过了玩家**。这条要动的是搭档 AI 的强度或托管范围，
不是关卡参数。

同一个思路我也拆了 B3，结论**相反**，值得写清楚免得被一起当成「AI 队友问题」：

| `duo-vs-star` 摆烂过的 72 关 | 关数 |
| --- | --- |
| 关卡自带 AI 队友（`lv.allies.length > 0`） | **7 关** |
| **玩家孤身一人、没有任何队友也赢** | **65 关** |
| （全 188 关里带队友的一共 10 关） | — |

**65/72 是没有队友的**，也就是说 B3 跟「队友替你打」无关，是**对手自己掉下台**
——正文 §2.3 按场地拆出的 `star-lift` 19/19、`night-hops` 16/19 说的就是这件事。
**B2 和 B3 根因不同，得分开修**：B2 调的是己方托管 AI，B3 调的是那两张台子的边界与敌方走位。
证据 `docs/qa/_evidence/window3-round3-rootcause.json`。
