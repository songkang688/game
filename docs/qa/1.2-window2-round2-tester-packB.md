## 二、走查结论

走查手法先交代一句，因为本轮有一处和第 1 轮不一样：`fight-king` 的对局画在 `canvas` 上，DOM 里读不出局面，
所以在界面旁边**逐帧复刻**了一份同参数的对局（同样的 `createMatch` 入参、同样的 AI 种子 `1234 + 档位 × 77`、
同样的 `acc += dt` 步进与超必杀定格），用复刻件算出「这一帧该按什么」，再把键真的 `keydown` / `keyup` 出去。

双人同屏串台的判据：只要 1 号位的键漏到 2 号位，复刻件立刻和界面对不上。

#### R2B-1 · `dark-chess` 双人同屏：朵朵的键在星星回合照样管用，还能替星星落子

- 位置：`src/games/dark-chess/view.ts:156` `onKey`。
- 现象：`w/s/a/d` 与 `f`/`g` 是**无条件**接的，只有方向键与 `l`/`k` 才判 `starTurn`：

```156:173:src/games/dark-chess/view.ts
  function onKey(e: KeyboardEvent): void {
    if (destroyed) return;
    const k = e.key.toLowerCase();
    const starTurn = state.turn === "star" && opts.humans.includes("star");
    const useArrows = starTurn || opts.humans.length === 1;
    let handled = true;
    if (k === "w" || (useArrows && k === "arrowup")) moveCursor(-1, 0);
    else if (k === "s" || (useArrows && k === "arrowdown")) moveCursor(1, 0);
    else if (k === "a" || (useArrows && k === "arrowleft")) moveCursor(0, -1);
    else if (k === "d" || (useArrows && k === "arrowright")) moveCursor(0, 1);
    else if (k === "f" || (starTurn && k === "l")) clickCell(cursor);
    else if (k === "g" || (starTurn && k === "k")) {
      selected = -1;
      targets = [];
      refresh();
    } else handled = false;
    if (handled) e.preventDefault();
  }
```

- 实测（双人同屏，轮到星星）：
  - 按朵朵的 `D` / `S`：光标 `0 → 1 → 9`，**跟着动了**（本该纹丝不动）。
  - 按朵朵的 `F`：手数行 `第 2 手 → 第 3 手`，提示 `翻开了一枚蓝子。`，回合切到 `轮到朵朵` ——
    **朵朵直接替星星把这一手下掉了**。
  - 反过来是对的：轮到朵朵时按星星的 `→` 光标 `9 → 9` 不动、按 `L` 手数停在 `第 3 手`。
- 还有一层：整块棋盘只有**一个** `cursor` 变量，两个人共用一个光标，所以就算把键位判对了，
  「各挑各的子」也还缺一个每人一份的光标。
- 影响面：双人同屏这一模式的键位失守，坐左边的人可以全程替右边的人下棋；单人模式不受影响
  （单人时方向键是别名，实测 `0 → 1` 正常）。
- 参照：这和窗口 2 第 1 轮包 A 在 `junqi-camp` 修掉的 `PA-JQ-1` / `PA-JQ-2` 是同一种形状
  （`06833df` 那一笔：「双人同屏一人一个光标，朵朵 WASD+F/G、星星 方向键+L/K 各管各的」），`dark-chess` 这一份还没跟上。
- 建议（本轮只记录，不动代码）：`w/a/s/d` 与 `f`/`g` 也加上 `duoTurn = state.turn === "duo" && opts.humans.includes("duo")`
  这道闸；`cursor` 拆成 `cursor[2]`，按 `state.turn` 取用。

#### R2B-2 · `hop-pads` 幽灵对战：玩家跳满 16 座就冻结，幽灵却是「跳 16 次」，同一条台序上分数天生对不齐

- 位置：`src/games/hop-pads/index.ts:948` `MATCH_HOPS = 16`、`:998` `playGhost(seed, diff, tier, MATCH_HOPS)`、
  `:469` `if (!goalHit && run.hops >= goal) { goalHit = true; frozen = true; ... }`。
- 现象：两边的「16」不是同一个 16。幽灵那边 16 是**起跳次数**，玩家这边 16 是**站住的台数**；
  弹簧台（`res.bonus`，「弹簧台!直接送你一跳」）会白送台数而不消耗起跳次数，于是幽灵一路多站好几座。
- 实测（`playGhost(..., 16)` 对「一路踩圆心直到 `hops >= 16` 被冻结」的满分玩家）：

| 局 | 幽灵（地狱）跳 16 次 | 满分玩家站满 16 座 | 差 |
| --- | --- | --- | --- |
| 第 1 局 | 站住 18 座 · 270 分 | 站住 16 座 · 230 分 | **−40** |
| 第 2 局 | 站住 20 座 · 310 分 | 站住 16 座 · 230 分 | **−80** |
| 第 3 局 | 站住 24 座 · 390 分 | 站住 19 座 · 290 分 | **−100** |
| 第 4 局 | 站住 20 座 · 240 分 | 站住 16 座 · 160 分 | **−80** |
| 第 7 局 | 站住 21 座 · 206 分 | 站住 16 座 · 108 分 | **−98** |

- 界面实证：地狱档一局踩圆心打下来，结算是 `地狱幽灵这次拿了 270 分,你 230 分`，顶栏 `你 0 : 0 地狱`。
- 连带一条：`TIER_NOISE` 里高手 0.05、地狱 0.015，两档的噪声都小到每一跳都落在圆心，
  所以 `expert` 与 `hell` 的成绩**逐局完全相同**（第 1 局都 270、第 2 局都 310、第 4 局都 240、第 7 局都 206）——
  选高手和选地狱在结果上没有分别。
- 影响面：对战模式最高两档「无论多完美都赢不了」，且两档手感一样；菜鸟 / 普通两档正常（普通 252 分是打得过的）。

  高手与地狱的噪声再拉开一档，否则档位选择器上半截是空的。

- 底账（八人循环赛，同档 lv4 对 lv4、无任何增益，每对 3 局共 21 局）：

  🍡 糯糯 76% · 🐼 墩墩 67% · ⭐ 星星 62% · ✨ 闪闪 62% · ☁️ 云云 52% · 🌱 绿绿豆 38% · **🌸 朵朵 33%** · 🐤 啾啾 14%
  —— 最强与最弱差 **62 个点**。朵朵的介绍写的是「全能型：速度、范围、威力都在中间，新手先选她准没错」，
  基础元气 100 也确实在中位，但实战垫底。

- 关于第 1 轮 `B-11` 的说法「被守擂增益放大」：本轮把同一批人挂上第 176 关那一档增益再跑一遍循环赛，
  差距是 48 个点（`0% ~ 48%`），比无增益的 62 个点**反而窄**，但平均胜率从 51% 压到 30%，
  朵朵直接被压成 **0/21**。所以准确说法不是「放大比例」，而是**把本来就弱的那几位压到零** —— 地板被削平了。
- 一句必要的坦白：这里的「玩家」是引擎自带的 lv4 通用 AI，它对每个角色用的是同一套决策，
  招式手感刁钻的角色天然吃亏，所以 62 个点里有多少是角色数值、多少是 AI 不会用，这份报告分不出来。
  但这正是仓库自己在 `curve.test.ts` 里采用的尺子，用同一把尺量出「默认角色后段 0/8、换人 5/8」这个对比是成立的。
- 影响面：格斗塔后 1/3（约第 125 关往后）在默认设置下推不动；换人之后可推。
- 建议（本轮只记录）：默认出战改成中位角色，或在连败若干次后在关内提示行补一句「换个小伙伴试试」；
