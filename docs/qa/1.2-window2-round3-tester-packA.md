## 四、重点复验一：`R2-PA-3` 的棋盘格例外**仍然成立**

## A.4 分歧项：`R3-PA-FS-1`（= 第 1 名的 `R3-PA-1`）建议重定为**严重**

两份报告指的是同一处：`allSettled` 要求**全场每一颗**连续 380ms 速度低于 22px/s
（`physics.ts` 的 `SETTLE_MS` / `SETTLE_SPEED`），而这一关的两条判负通路都挂在它上面：

```
src/games/fruit-stack/index.ts:378   if (overLine(world)) { ... }        // overLine 也只看「已静止且过了宽限期」的果子
src/games/fruit-stack/index.ts:384   if (opts.limited && left() <= 0 && allSettled(world)) { ... }
```

判过关的 `goalMet` **不**看 `allSettled`，所以**还赢得了，就是再也输不了**。

第 1 名的定级理由是「要每一手都挑最差落点才逼得出来，正常玩法撞不上」。**本节的三组取证不支持这个前提：**

**（一）随机落点就够了，不用挑最差。** 完全模仿真人 / 电脑乱摆，每投一颗都给 6 秒纯空转的机会停稳：

| 关 | 可放 | 弹性 e | 20 盆里有几盆再也停不下来 | 平均投到第几颗卡住 |
|---|---|---|---|---|
| 第 1 关 | 26 | 0.160 | **2 / 20** | 21.5 |
| 第 132 关 | 43 | 0.399 | **9 / 20** | 28.6 |
| 第 188 关 | 38 | 0.200 | **20 / 20** | 21.7 |

**第 188 关 20 盆全中**，平均投到第 22 颗（预算 38 颗）就再也停不下来。
也就是说这一关基本上「要么在第 22 颗之前达标过关，要么这一盆永远收不了场」。

**（二）界面上真按也撞得到。** 第 132 关落点一步不挪（就用默认的盆正中央）把 43 颗投完，
HUD 停在「朵朵的果盆，427分，最大「苹」，盆里16颗，**剩0颗**」，**再空跑 100 秒也不出结算浮层**，
这时候拨一下 `D` 也救不回来。那一盆 16 颗里有 10 颗静不下来，速度 58 / 88 / 115 / 130 px/s ——
不是「小幅滚动」，是真的一直在跑。

> 本节的走查脚本之所以还量得到别的，是因为 `dropUntilSettled` 每投一颗先左右拨一下落点，
> 把撞上的概率压下去了 —— **只是压低概率，不是绕过**。

**（三）电脑自己就会把自己冻住（`R3-PA-FS-2`，第 1 名未发现）。**
进人机对战、**人一次都不碰键**：电脑按自己的算法投了 29 颗（两次投放最大间隔只有 5 步，节奏很稳），
最后一颗落在第 109 步之后**再也没投过** —— 又空转 491 步（≈283 秒）一动不动，收场浮层也一直不出。
这时候人再按 6 下 `F`，朵朵这边**照常投得动**（0 → 5 颗），电脑仍死死停在 29 颗。

根因还是同一处 —— 电脑决定下一手之前先等自己那盆停稳：

```
src/games/fruit-stack/index.ts:341   if (!allSettled(world) || aiWait > 0) return;
```

电脑那盆一进死状态，`aiTarget` 永远是 `null`，电脑再也不出手；
对战这一局的收场条件（一方达标 / 一方越线）此时也都够不着 —— **这一局怎么等都不会结束**。
对战的 `drops` 是 9999，不存在「电脑果子用完」这回事。
这也解释了本节铁则 4 打出来的「🏆 朵朵拿下整场! 朵朵 3 : 0 星星」：末局收场前投放数是**朵朵 81 : 电脑 28**，
不是电脑棋差，是电脑中途就不打了。

**为什么建议算严重.** 按本窗三轮通用的分级口径，「严重＝一整条铁则不成立」：
铁则 2 / 3「真赢 + 真输到结算」在 fruit-stack 第 188 关的**随机玩法下 20/20 不成立**（输不了，只会吊着），
铁则 4「对战玩到结算」在人机对战里也会不成立。
它确实不崩、不脏数据、退得出去（这几点与第 1 名的观察一致），所以**不到阻断**；但已经超出「一般」。

**共识部分**：修法要动物理收敛判定，会波及 188 关的过关判定与星级门槛，
**本轮不该改**（测试员本来也不写 `src/`）。两份报告在「这一轮不动手」上没有分歧，
分歧只在「记成一般还是严重、发布前要不要先给一条兜底」。
本节建议至少先落一条**低成本兜底**（果子用完后连续 N 帧无人达标就按当前分数结算 / 给电脑的等待加上限），
再谈把物理收敛正经修一遍。

**不是回潮.** `physics.ts` 自建款期以来没被任何人改过（`git log` 只有三个建款 commit），
第 1/2 轮的修复也没碰过合成 / 物理，属于一直在、第 3 轮才翻出来。
