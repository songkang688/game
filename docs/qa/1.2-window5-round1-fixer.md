**W5-F-01 · 严重 · `color-fun` 画室读到坏存档会崩，而且崩完整间画室就废了**

- **怎么找到的**：按本轮口径补测「存档损坏 / 崩溃入口」时顺着沙盒存档层往上读出来的。
- **成因**：`sandbox.ts` 的 `normalizeWork()` 只管线稿下标是不是个 **≥0 的有限数**，它**不认识 `PICTURES` 有几幅**——存档被改坏、或者从装过新版（线稿更多）的机器退回旧版，都会留下一个指不到画的下标。画廊那一格本来就写着 `?? PICTURES[0]`，缩略图看着好好的；可**「点开旧作接着涂」**那条路没有兜底：`onWork()` 直接把它赋给 `picIndex`，`renderCanvas()` 再去读 `PICTURES[picIndex].regions`。
- **真机证据（修复前，`51f99ae` 单独构建的产物）**：往 `yiduo-yixing.clf.sandbox.v1` 写一张 `{pic: 999}`，开画室、点那张作品 →
  `TypeError: Cannot read properties of undefined (reading 'regions')`。
  更要紧的是**崩完还回不去**：接着再涂一笔 / 撤销 / 清空 / 换线稿，又抛 2 次同样的异常——`picIndex` 已经停在 999，画室从此点什么都没反应，只能退出游戏重进。这就是判**严重**而不是一般的理由（可复现的崩溃 + 功能不可用，只是要先有一份坏存档）。
- **修法**：`sandboxUi.ts` 新增纯函数 `safePicIndex(i)`，越界 / 负数 / 小数 / `NaN` 一律回到第一幅；`onWork()` 与 `renderGallery()` 都走它，两处不再各写各的兜底。**不动存档层**——`sandbox.ts` 故意不认识 `PICTURES`，把游戏数据塞进存档层反而是退步。
- **新增回归**：`src/games/color-fun/sandboxRobust.test.ts`。第一条同时钉两件事——存档层**确实会放行**越界下标（证明这个入口不是我编的），以及不收口**真的会抛**；后面几条钉收口行为与两处接线。
- **先红**：`AssertionError: expected [Function] to not throw an error but 'TypeError: Cannot read properties …' was thrown`（4 条全红，`safePicIndex` 当时还不存在）。
- **修复后真机复测**：同一段操作，JS 异常 **0** 个，画布正常换成第一幅、8 块区域都画得出来，后续涂 / 撤销 / 清空 / 换线稿也都 0 异常。

**W5-F-02 · 一般 · `word-garden`「百发百中」的题面自己把答案摆出来了（6 道题）**

- **成因**：这条成语里「百」出现两次，`blank: 2` 挖的是**后面**那个，题面渲染成「**百**发□中」——前面那个「百」明晃晃留在题上，孩子照着抄就行。学习优化员那一轮把三条**释义**的自指修干净了，但守门用例只扫 `ask`（释义句），没扫 `promptHTML`（挖了空的成语本身），所以这一条一直没露头。「每一次都正中目标」这句释义本身是干净的。

**W5-F-04 · 一般 · `color-fun` 画室「涂过一笔之后 Esc 就不灵了」（补 W5-L-05 的另一半）**

- **成因**：`keydown` 挂在 `.clf-sheet` 上，只有焦点还留在画室里才收得到。线稿上的色块是 SVG 图形、不可聚焦，点它一下浏览器会把焦点交给**最近的可聚焦祖先**；画室没有 `tabindex`，焦点就一路交到画室外面去了，Esc 从此冒不到画室上——偏偏「点一下涂个颜色」就是进画室要做的第一件事。
- **真机前后对照**：修复前，涂完一笔 `document.activeElement` 是 `DIV`（没有 `clf-sheet` 类），按 Esc **画室还在**；修复后 `activeElement` 是 `DIV.clf-sheet`，按 Esc **画室关掉了**，焦点回到「🎨 自由涂色（不计分）」，平台暂停面板没有被同一下 Esc 顶出来。
- **修法**：给 `.clf-sheet` 补 `tabindex="-1"`。用 `-1` 是为了只接鼠标点击带来的焦点、**不往 Tab 序里插一站**——这也是 `role="dialog"` 容器的通行写法，和 W5-L-04 已经做的初始焦点 / 焦点归位是同一套东西的最后一件。
- **守门**：`sandboxRobust.test.ts` 加一条源码巡检，钉 `role="dialog"` 与 `tabindex="-1"` 一起在位。

### A6 · 收尾时新发现的一条阻断（W5-F-07，根因卡在本档禁改文件上）

**这一条是收尾 rebase 时才有条件发现的**：档B 测试员的报告（`c523100`）在我干活期间落到了同一条分支上，记了一条阻断 **W5-B-01**——`src/styles.css` 的 `.game-stage { overflow:hidden }` 是个定高硬裁剪，**内容超出既不滚也不给提示**，谁的内容一高谁就中招。他们只量了自己那五款。我把同一把尺子拿回来量了档A 五款，**砸中两款，而且比档B 那几款更靠前**。

**量法**（和档B 一个口径，但我多加了一步决定性验证）：三档视口各进第 1 关，把 `.game-stage` 的可视高与 `scrollHeight` 拉出来，再对每一颗可点按钮做 `document.elementFromPoint(中心点)` ——**返回的不是这颗按钮，就是真的点不着**。这一步很要紧：程序化 `el.click()` 在被裁掉的元素上照样能触发，**档A 测试员上一轮之所以能把 color-fun 第 1 关打到 ★★★，多半就是这个原因**；换成真实鼠标坐标就点不响了。

| 款 | 390×844（舞台 738） | 360×720（舞台 618） | 360×640（舞台 538） |
| --- | --- | --- | --- |
| `color-fun` 第 1 关 | 内容 **949**，裁 211 —— **整条调色板（粉/棕/黄/蓝/红 5 颗）中心落在 y=955，视口只有 844，`elementFromPoint` 返回 `null`（点空气）** | 内容 918，裁 300 —— 调色板 5 颗 + 🔍 缩放键共 **6 颗点不着** | 内容 874，裁 336 —— 同样 6 颗 |
| `red-blue-race` 第 1 关 | 内容 777，裁 39 —— 按钮都还够得着 ✅ | 内容 807，裁 189 —— **👟左脚 / 👟右脚 / 🦘跳 三颗触屏键 `elementFromPoint` 全部认不到** | 内容 807，裁 269 —— 同样三颗 |
| `landlord-cards` 第 1 关 | ✅ 0 | ✅ 0 | 裁 117 —— ⏸ 暂停点不着 1 颗 |
| `clock-house` / `word-garden` 第 1 关 | ✅ 0 | ✅ 0 | 裁 43–58，但那一截里没有按钮，**0 颗点不着** |

- **为什么判阻断**：`color-fun` 第 1 关要按指令涂四种颜色，**选不了颜色就一笔都涂不了**——在 iPhone 14 Pro 这个主流尺寸（390×844）上就已经这样了，不是小屏才有的边角。`red-blue-race` 在 360×720 上三颗触屏键全灭，纯触屏的孩子开不了跑（键盘还能玩，但这是手机）。都属于「点不着」，不是「难点」。
- **救不回来**：舞台 `overflow-y:hidden`，用户既滑不动也没有滚动条；`document.documentElement.scrollHeight > clientHeight` 为 **false**，页面本身也不滚。我程序化把 `stage.scrollTop` 推到 219 / 308 之后同一个点就能点响——**证明按钮是活的，只是够不着**，和档B 的结论一致。
- **根因分两半**：
  - **平台侧（`交给窗口1`）**：`src/styles.css` 的 `.game-stage{flex:1;min-height:0;overflow:hidden}`，以及 `level99.ts` 渲染的 `.l99-stage-wrap` 同样是 `overflow-y:hidden`——**两个都在本档明令禁改的清单里**（`src/ui/**` 与 `level99.ts`）。这一半我一行没动。建议按档B 的说法改成 `overflow-y:auto` 或给舞台一个滚动兜底。顺带一个数：`.l99-stagebar`（返回 / 关卡名 / 攻略 / 跳过）在 390×844 上就吃掉 **116px**，是各款共同的固定开销。
  - **本档侧（可自己修，但本轮没修，理由在下面）**：`color-fun` 的 `ui.ts` 里 `.clf-stage{min-height:${CANVAS_MIN_VH}vh}`，`CANVAS_MIN_VH = 55`。**问题就出在 `vh` 上——它量的是整个窗口，可这一款只住在窗口的 ~70%（壳层顶栏 + `.l99-stagebar` + 本款自己的画室入口条先吃掉一大截）。** 390×844 上它给一幅**实际只有 236px 高**的画预留了 **464px**，凭空空出 228px，正好就是裁掉的那 211px。
- **本轮为什么不动它**：
  1. 主根因在 `src/styles.css` 与 `level99.ts`，**本档明令禁改**，平台那一半不落地，游戏这一半改了也验不出端到端的效果；
  2. `upgrade12.test.ts` 有一条既有断言钉着 `CANVAS_MIN_VH >= 55`（「画布至少占屏高 55%」是这一款写进用例的手感承诺），改它属于**动既有手感**，本轮纪律写着这种改动要小而稳、要带成套回归；
  3. 我算过账：就算把 `.clf-stage` 从 `55vh` 换成按画布自身 4:3 比例的 `min(55vh, 75vw)`，390×844 上也只省得下 172px，内容 777 对舞台 738 **仍然超 39px**；360×720 上省 126px 后还超 174px。**光靠缩本档内容清不掉这条阻断**，平台那一半是必须的。
- **一个必须记下来的相互作用**：学习优化员这轮把 `.rbe-open` 从 40px 提到 44px（W5-L-03，方向完全正确），两颗胶囊在窄屏上折成两行，`.rbe-bar` 因此占到 **96px**。**热区变高和纵向预算是一对矛盾**——在一个会硬裁的舞台里，把热区补到 44px 就等于把更多东西推到裁切线以下。第 2 轮修这条时要把两件事一起看，不能只顾一头。
- **给第 2 轮 / 窗口1 的具体建议**：平台先把 `.game-stage` 改成可滚（或 `overflow-y:auto`），落地后本档再做两件事——① `color-fun` 把 `.clf-stage` 的预留从「窗口高的 55%」改成「**可用高度**的 55%」（或按画布 4:3 自适应），同步把 `upgrade12.test.ts` 那条断言的口径从 `vh` 改成可用高度；② `red-blue-race` 让 `.rbe-bar` 两颗模式入口在窄屏并成一行（省 52px），同时保住 44px 热区。两件都在本档目录内。

### B1 · 复审手法：为什么不认 `el.click()`

这一轮的判据只有一条——**`document.elementFromPoint(元素中心点)` 拿回来的是不是它自己**（或它的后代 / 它的祖先）。拿不回来就叫「点不着」，不管程序化点它响不响。

为什么把这条写死：被 `overflow:hidden` 裁掉的元素，`el.click()` **照样触发**，回调照样跑，日志照样绿——测试员 W5-B-01 里那句「程序化把 `scrollTop` 推到底之后同一个点就能点响」说的正是这件事。上一轮之所以会把两条没修好的当成修好了，根子就在这儿。

还有一处更隐蔽的假绿，本轮专门堵上了：探针一开始用 `el.scrollIntoView()` 判「滚一下够不够得着」——**它连 `overflow:hidden` 的容器都推得动，而用户推不动**。改成只认 `overflow-y/x` 为 `auto` / `scroll` 且真有可滚距离的祖先，手动写 `scrollTop` / `scrollLeft`。改完之后，`music-stars` 七声沙盒那两个键从「绿」变回「红」——这才是真机上的样子。

四档视口 × 五款 × 各 3–5 关 = **72 个组合**逐个扫。触屏手势另用 `Input.dispatchTouchEvent` 发**真实手指事件**（`touchStart` / `touchMove` / `touchEnd`），因为「这一行滚不滚得动」和「点两个点通不通」这两件事，只有真手指试得出来。

### B3 · 补修与新增回归（先红后绿）

#### W5-F-08 · 阻断 · 矮屏「自滚」是空转的（`shape-kingdom` / `music-stars`）

- **红**：真机 360×640。`.shk-draw` 内容高 517、舞台看得见 408，`scrollHeight - clientHeight = 0`；`.mst-wrap` 内容高 416、看得见 362，同样是 0。滚动条从来没出现过，「✅ 我摆好了」与声音设置栏照旧 `elementFromPoint` 返回 null。
- **根因**：矮屏那一档写的是 `max-height:100%`。**百分比高度要有一个定高父级才算得出来**，而壳层这条链上 `.l99-stage` / `.l99-stage-wrap` 全是内容撑出来的 `auto` 高——它们自己先长到内容那么高，`100%` 于是等于内容自己的高度，永远钳不住。真正定高的那一层是 `.game-stage`（平台文件，**交给窗口1**）。
- **绿**：本款够不着 `.game-stage` 的 CSS，但够得着它的**盒子**。新增 `fitIntoStage()`：往上找最靠近的裁切祖先（`overflow-y` 为 `auto`/`scroll`/`hidden`），量它的下沿，把「从自己顶边到那条线还剩多少像素」写成自己的 `max-height`（内联样式，优先级高过那条 `100%`）。装得下就把 `max-height` 与 `overflow-y` 两样都还回去——高屏上不许凭空多出一个滚动容器（那会把 `.shk-board` 的投影裁掉）。接进 `shape-kingdom/draw`、`music-stars` 的战役 / 进阶 / 沙盒三个入口，**换题与转屏各重算一次**，`destroy` 时拆监听。CSS 里那行 `max-height:100%` 留着并加注说明它今天钳不住，等平台给舞台链定了高就自动接上，两边不打架。

#### W5-F-09 · 阻断 · `shape-kingdom` 答题屏的选项还是点不着

#### W5-F-10 · 严重 · `music-stars` 七声沙盒两端的键仍然按不到

- **红**：上一轮给键盘那行挂了 `mst-keys-scroll`（`overflow-x:auto` + `touch-action:pan-x`），报告记为「从点不到变成滚得到」。用 `Input.dispatchTouchEvent` 发真实手指划动一试——**这一行根本滚不动**，`scrollLeft` 纹丝不动。原因是键身自己还挂着 `touch-action:none`，而键 44px、缝只有 4px，**一根手指落哪儿都在键上**，浏览器于是不认这是一次横滑。「哆」和「高哆」只是从「切在屏外」变成了「滚不过去」，结果一样：按不到。程序化 `el.click()` 照样绿，这就是上一轮漏掉它的原因。
- **绿**：三处一起改。① `.mst-keys-scroll .mst-star{touch-action:pan-x}`——只在滚起来那一档让出横向手势，不滚的时候键仍是 `touch-action:none`，按下去照旧出声；手指真的横着划走时浏览器补一个 `pointercancel`，音会正常停。② `.mst-sky` 的 `max-width` 从 `SKY_MAX_PX` 改成 `min(SKY_MAX_PX,100%)`——沙盒把键盘装在一个 shrink-to-fit 的空 div 里，那种盒子的宽度取自内容的 `max-content`，键排有多宽它就有多宽，整块星空于是探到舞台外面去，**横向再怎么滚也把两端的键滚不回可视区**；`.mst-sb-keys` 同时补 `width:100%;min-width:0`。③ `createStarBoard` 新增 `host` 参数，直接量真实容器的 `clientWidth`——`boardWidth()` 只减得掉 `.mst-wrap` 自己的内边距，减不掉壳层顶栏、`.l99-stage` 的内边距和舞台描边，360px 上要多估 40–60px（实测真实容器只有 292px），于是「算着放得下、实际放不下」。沙盒挂进文档之后 `relayout()` 一次，因为游离节点的 `clientWidth` 恒为 0。
- **真手指复测**：390×844 / 360×720 / 360×640 / 320×640 四档，一次横划把 `scrollLeft` 推到底（0→54 / 0→76 / 0→76 / 0→108），逐个滚过去 **8/8 键全部够得着**。

#### W5-F-11 · 阻断 · `red-blue-tap` 战役竞技场被裁，点是随机摆的所以「时灵时不灵」

- **两份报告里都没有这一条**，是复审时补出来的。测试员 W5-B-02 抓的是**双人对战**那四颗键，学习优化员照着改成了 2×2；**战役这一半从来没人量过**。
- **红**：真机 320×640 第 188 关。竞技场 CSS 高 280，上面那一截（比分条 + 道具芯片在 320px 宽各折成两三行）把它顶到 y=416，舞台底边只到 626——**下面 70px 里的点一颗都 `elementFromPoint` 不到**。点是按百分比随机摆在竞技场里的（`placeDot` 写的是 `left/top: n%`），所以落在上半截就按得着、落在下半截就按不着，表现成「时灵时不灵」而不是「一直坏」——比一直坏更难查。这一款整个玩法就是「按亮起来的那颗点」，按不到等于这一局作废。

#### W5-F-13 · 一般 · `shape-kingdom`「点两个点」这条路从来没通过（测试员 W5-B-05）

学习优化员把它留到了第 2 轮（W5-L-20），理由是「输入语义的改动」。本轮作为收口人评估下来它**当轮就能收干净**，而且读数那行白纸黑字写着「点两个点（或者按住拖）」，承诺了却是死的，就修了。

- **红**：`onDown` 一律把 `corner` 顶成当前点，`onUp` 又 `setRect(同一点, 同一点)` 拿到 0×0 并把 `corner` 清成 `null`，等 `click` 派发过来 `corner` 永远是 null——每一下都只是「摆上第一个点」，凑不成一对。
- **为什么既有用例是绿的**：那条用例只 `fire('click')`，**从来没走 `pointerdown` / `pointerup`**，真机的事件顺序根本没被覆盖。这是本轮抓到的第三种假绿。
- **绿**：把「原地抬起」判成一次点击。`onDown` 只记起点、一个字都不动 `corner`（万一这是原地点一下，上一次点的那个点还得留着凑对）；`onMove` 第一次真的滑到别的点上才置 `movedAway` 并接管；`onUp` 分两条路——没滑走走 `tapDot`，滑走了才是原来那套拖动。点的 `click` 只接 `detail` 为 0 的合成事件（键盘 Enter / 空格），手指与鼠标补出来的 `click`（`detail ≥ 1`）一律让开。**没有用「吞掉下一次 click」的标志位**——松手时不在任何点上就不会有后续 click，那个标志位会漏收，把下一次真的键盘操作也吞掉。
- 先红后绿实测：新增的三条用例（点两下 / 拖一次且拖完的 click 不许再点一下 / 键盘 `detail=0`）在改之前**前两条红**，改之后 48 条全绿。CDP 真手指复测 390×844 / 360×720 / 320×640 三档，点两下都拉得出 4×3，拖动手感不变。

### C1 · 复审手法：为什么不认 `el.click()`

`el.click()` 是**直接对着 DOM 节点派发事件**，它完全绕开了「这个点上到底是谁在最前面」这道题。这一档抓到的三条阻断（W5-F-14 / 15 / 16）全部是这道题答错——按钮、场地、饭碗都在 DOM 里、都能 `querySelector` 得到、`el.click()` 都会正常触发回调，可真手指按下去，`document.elementFromPoint(盒子中心)` 拿回来的是**别的元素**（或者 `null`）。用 `el.click()` 验，三条全是绿的。
