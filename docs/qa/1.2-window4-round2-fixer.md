### 二、C2-02 怎么修的

现象是「`bubble-aim` 无尽把屏幕清空之后整局冻住」。拆开看是**两层**，两层各自都得修。

#### 里层：补货行的长度不看 `flip`

`afterEndlessShot()` 清屏后补货走的是

```ts
for (const line of endlessStartRows(ENDLESS_COLORS, Math.random, 2)) descend(grid, line);
```

`endlessStartRows` 按 `rowLen(0, r)` 出长度，返回的永远是「9 个字符、然后 8 个」；
而 `descend` 要的是 `rowLen(g.flip ^ 1, 0)`，随已压行数的奇偶在 8 / 9 之间来回。
`flip === 0` 时要 8 却给 9，`parseRow` 直接抛。开局 4 行是 `parseLayout` 铺的、不算 `descend`，
所以初始 `flip = 0`——**第一次清屏就踩在崩的那一半上**。

**修法**：给 `endlessStartRows` 加第四个参数 `flip`，默认 0。

```ts
export function endlessStartRows(colors, rand, rows = ENDLESS_START_ROWS, flip = 0): string[]
```

循环里改用 `rowLen(flip, r)`。补货那句传 `grid.flip ^ 1`：

```ts
for (const line of endlessStartRows(ENDLESS_COLORS, Math.random, 2, grid.flip ^ 1)) {
  descend(grid, line);
}
```

`flip ^ 1` 这个值是推出来的、不是试出来的：第 r 次 `descend` 需要的长度是
`rowLen(F ^ 1 ^ (r & 1), 0)`，而 `rowLen(x, r)` 的奇偶是 `(r & 1) ^ x`，
两边对齐解出 `x = F ^ 1`。所以整批行一次性按 `flip = F ^ 1` 生成，逐行都对得上。

默认值 0 保证另一处调用（`parseLayout(endlessStartRows(...))`，它自己按 `rowLen(0, r)` 解析）
**一个字节都没变**，无尽开局仍然是原来那批行。

#### 外层：一次异常就把整条 rAF 循环带走

这才是「卡死」而不是「少补一行」的原因。`raf = requestAnimationFrame(tick)` 写在
`tick()` 的**最后一行**，异常一抛，重新排帧那句永远执行不到。

**修法**：把排帧句挪到 `destroyed` 闸后面的第一行。

```ts
function tick(now: number): void {
  if (destroyed) return;
  raf = requestAnimationFrame(tick);   // ← 先排下一帧,再干活
  ...
}
```

这样逻辑再出问题，最坏也只是这一帧画歪，不会把整局带走。
`destroyed` 闸在排帧之前，所以 `destroy()` 之后照样一帧都不会再排（见下面的泄漏复核）。

**同一处通道另外两款也有**：`alien-seek` 的 `frame()`、`snake-snack` 的 `frame()`
排帧句同样压在最后一行。这次一起改了——不是它们现在有 bug，是这条通道一旦被别的改动
碰到，症状就是「整局冻住」这种最难查、对小朋友最劝退的一类。
`box-hamster` 只有挂载时量一次格子那一发 rAF，不是循环；`memory-cards` 压根没有 rAF。

#### 3）`destroy` 仍旧收得干净

本轮有两处动了运行时，都各自复验：

- **`bubble-pop/index.ts` 的 `tide()` 现在会连推两行。**
  改法上刻意让循环体只调 `pushUpRow`（纯函数），
  定时器仍旧全部经 `bag.after(...)`，一处都没绕过口袋。
  复验：连开连关 20 轮，假宿主里一个活口都不剩；
  收摊之后再排一件活儿会当场就地收掉，`alive` 立刻转 `false`。
  顺手把这一处的两个 `as` 断言去掉了（`grid` 本来就是 `number[][]`，不需要转）。
- **`adventure-king/index.ts` 的种子从「每间一摇」改成了「一趟一个」。**
  `runSeed` 是 `mountEndlessCastle` 里的 `const`，随这一趟一起走，
  不进模块作用域、不挂全局，`destroy` 之后自然消失。
  复验：`Disposer` 连收 10 件一把清零，`dispose` 两次不会把同一件事收两遍。
