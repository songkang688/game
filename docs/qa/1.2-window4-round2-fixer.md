### 二、C2-02 怎么修的

现象是「`bubble-aim` 无尽把屏幕清空之后整局冻住」。拆开看是**两层**，两层各自都得修。

#### 里层：补货行的长度不看 `flip`

`afterEndlessShot()` 清屏后补货走的是

```ts
for (const line of endlessStartRows(ENDLESS_COLORS, Math.random, 2)) descend(grid, line);
```

`endlessStartRows` 按 `rowLen(0, r)` 出长度，返回的永远是「9 个字符、然后 8 个」；
而 `descend` 要的是 `rowLen(g.flip ^ 1, 0)`，随已压行数的奇偶在 8 / 9 之间来回。
`flip === 0` 时要 8 却给 9，`parseRow` 直接抛。开局 4 行是 `parseLayout` 铺的、不算 `descend`，
所以初始 `flip = 0`——**第一次清屏就踩在崩的那一半上**。

**修法**：给 `endlessStartRows` 加第四个参数 `flip`，默认 0。

```ts
export function endlessStartRows(colors, rand, rows = ENDLESS_START_ROWS, flip = 0): string[]
```

循环里改用 `rowLen(flip, r)`。补货那句传 `grid.flip ^ 1`：

```ts
for (const line of endlessStartRows(ENDLESS_COLORS, Math.random, 2, grid.flip ^ 1)) {
  descend(grid, line);
}
```

`flip ^ 1` 这个值是推出来的、不是试出来的：第 r 次 `descend` 需要的长度是
`rowLen(F ^ 1 ^ (r & 1), 0)`，而 `rowLen(x, r)` 的奇偶是 `(r & 1) ^ x`，
两边对齐解出 `x = F ^ 1`。所以整批行一次性按 `flip = F ^ 1` 生成，逐行都对得上。

默认值 0 保证另一处调用（`parseLayout(endlessStartRows(...))`，它自己按 `rowLen(0, r)` 解析）
**一个字节都没变**，无尽开局仍然是原来那批行。

#### 外层：一次异常就把整条 rAF 循环带走

这才是「卡死」而不是「少补一行」的原因。`raf = requestAnimationFrame(tick)` 写在
`tick()` 的**最后一行**，异常一抛，重新排帧那句永远执行不到。

**修法**：把排帧句挪到 `destroyed` 闸后面的第一行。

```ts
function tick(now: number): void {
  if (destroyed) return;
  raf = requestAnimationFrame(tick);   // ← 先排下一帧,再干活
  ...
}
```

这样逻辑再出问题，最坏也只是这一帧画歪，不会把整局带走。
`destroyed` 闸在排帧之前，所以 `destroy()` 之后照样一帧都不会再排（见下面的泄漏复核）。

**同一处通道另外两款也有**：`alien-seek` 的 `frame()`、`snake-snack` 的 `frame()`
排帧句同样压在最后一行。这次一起改了——不是它们现在有 bug，是这条通道一旦被别的改动
碰到，症状就是「整局冻住」这种最难查、对小朋友最劝退的一类。
`box-hamster` 只有挂载时量一次格子那一发 rAF，不是循环；`memory-cards` 压根没有 rAF。

### 二、W4A-07（严重）· 无尽砖塔：打得越快，死得越早

**病灶**。`towerSpeed(rowsCleared)` 把下压速度挂在「已经清了几行」上。
于是清一行的**唯一**结果是墙压得更快——把奖励做成了惩罚。
第 2 轮测试员用 2 / 3 / 4 / 6 砖每秒四种手速各跑一遍，
四种手速**都活不过 40 秒**，而且手速越高活得越短。

**修法**（`src/games/brick-break/logic.ts`）：

1. `TowerState` 加一个 `elapsed`（这一趟玩了多少秒）；
   `towerSpeed(elapsed)` 改成只跟时间有关：
   `TOWER_SPEED_BASE = 7` 起步，`TOWER_SPEED_RAMP = 0.075` 每秒加，
   封顶 `TOWER_SPEED_MAX = 17`。**清行不再加速**。
2. 新增 `squeezeTower(rows)`：把空掉的行整行抽走，上面的砖跟着往下落一格。
   清一行换来的是**整堵墙往上退一格**——真正的喘息。
3. 新增 `rowSettled(row)` + 钢砖自碎：一行里除钢砖以外都清光时，
   这一行的钢砖自己碎掉。钢砖不再越攒越厚，把塔底堵成一堵拆不动的墙。

**验证**：`walkthrough.r2.test.ts` 里那几条特征化用例改成了「已修」口径——
四种手速都撑得住，而且**手速越高活得越久**（奖励方向掰回来了）。

### 三、W4A-11 / W4A-12（中等）· 两款「无尽」都不是无尽

两条是同一个病：出场表是一张**写死长度**的表，表走完就没有下文。

- 接住小水果：320 颗的表 156 秒下完，然后**自己结算**。
- 戳戳小气球：900 个球的表 341 秒出完，然后**天空彻底空掉**——
  既不出球也不收场，画面就那样挂着，只能按退出。比提前收工更难受。

**修法**：把「一整场的表」改成「一段的表」，快见底就续下一段。

| | 接住小水果 | 戳戳小气球 |
| --- | --- | --- |
| 一段多长 | `RAIN_CHUNK = 320` 颗 | `FEST_CHUNK = 900` 个 |
| 提前多久续 | 还剩 `RAIN_LOOKAHEAD = 40` 颗 | 还剩 `FEST_LOOKAHEAD = 60` 个 |
| 续段函数 | `rainExtend(prev, seed, fromWave, count)` | `festExtend(prev, seed, count)` |
| 接缝怎么接 | 从上一颗必接果的**落点 + 落地时刻**起算 | 接上一个球的时刻 + 封顶的 360ms 间隔 |
| 节奏接不接得上 | 间隔与落速按**绝对波次**算，续段接着变密变快 | 同上 |
| 收场还剩几个出口 | 一个：三颗爱心用完 | 一个：放跑三个 |

接缝是这两条改动里唯一容易翻车的地方。水果雨的落点原来从「篮子站在正中、
时刻为 0」起排，续段若照搬，生成器会以为篮子有几百秒可以慢慢走，
第一颗就能摆到屏幕另一头。为此给 `PlanOptions` 加了 `startT`，
`layoutPlan` / `predictBasket` / `markReachable` 都认这个起算时刻。
用例逐颗核过整条表（含接缝）的可达性：**篮子一次都不用瞬移**。

续了 8 段之后水果雨排到 20 分钟以后，续了 10 段之后气球节排到 55 分钟以后，
两边都还在正常出场。礼物球「同一时间只挂一个」的规矩在续段里照样守得住。

### 四、W4A-15（中等）· 第八章那五关「达标也会翻车」

**病灶**不在关卡结构，在数值口径：精英的血量是照「满状态迎战」配的
——首领关索性在门口摆一块整装石，就是这个道理。可普通关没有整装石，
一路打过来的消耗**全带进收尾那一场**。第 135 / 138 / 139 / 153 / 155 关
就卡在这儿，达标勇者六局输一局。

**修法**（`src/games/brave-path/levels.ts` 新增 `easeClimaxElite`）：
到收尾精英跟前时若已经打过架，这只精英的血量与气势各松 `CLIMAX_EASE = 0.9`。
「疲劳」按上一处歇脚石之后打了几场算，精英记两场；一场都没打过就不松
（那种情况本来就是满状态迎战）。

**为什么不是加歇脚石**：试过三种加法（把中间的宝箱换成歇脚石、在收尾前插一步、
把收尾精英降成小怪），分别要改 37 / 76 / 29 关，而且前两种改完仍有 2~4 关不稳。
按疲劳松一成只碰 52 关的**数值**、一步路都不动，反而把 5 关全部清零。

**验证**：188 关逐关六局六过，原来那 5 关加倍到 14 局也稳得住；
第 155 关的三连打结构原样保留；松一成之后收尾精英仍明显强过同关小怪。

### 五、W4A-10（建议）· 新玩家永远见不到守关

守关原本每 8 层一位，可 1 级的朵朵大概第 4 层就走不动了——
第一趟永远见不到守关长什么样，也就体会不到「练一练能多走几层」的甜头。

**修法**（`src/games/brave-path/logic.ts`）：第一位守关挪到第 4 层
（`FIRST_GUARDIAN`），之后仍是每 8 层一位。光挪位置会把它变成一堵翻不过的墙，
所以配套加了 `guardianThickness(depth)`：浅层守关从 1.5 倍起步，
一路爬到第 16 层才回到原来的 2.3 倍。

| 存档等级 | 改前探底 | 改后探底 |
| --- | --- | --- |
| 1 级 | 4 层 | 3~4 层（**撞得上第 4 层守关，五局赢两局**） |
| 8 级 | 7 层 | 7 层 |
| 20 级 | 16 层 | 16~17 层 |
| 60 级 | 26~30 层 | 26~30 层 |

见得着、偶尔打得赢，深层的分量一点没少。

### 六、W4A-14（轻微）· 一半是量错的

第 2 轮测试员用「最慢能允许多久点一下」量每一关的松紧，得出两条：
相邻两关差三倍、最后一章反而松。本段逐条复量：

**「相邻两关差三倍」——尺子用错了。** 第 8 / 10 章是**两种玩法轮着来**的
（`t % 3 === 2 ? "color" : "free"` / `t % 2 === 0 ? "free" : "color"`）。
自由关要戳掉飘上来的每一个球；指定色关一屏里该戳的只占五分之一，
自然可以慢五倍。拿同一把尺子量这两种关，差三倍是必然的——
就像不能拿跑步的配速去量跳绳。被点名的第 140 / 141 关正好一关指定色、一关自由。
按玩法分开量，**每一章、每一档玩法自己都是干净的下坡**，已立成逐章逐玩法的守护用例；
同为自由关的相邻样本，松紧差不到 1.5 倍。

**「最后一章反而松」——这一半是真的，已改。** 只比自由关：
第 7 章紧到 0.8 秒、第 8 章 0.6 秒，可收尾的第 10 章原来也只有 0.8 秒,
末章反倒成了喘气的地方。把第 10 章的 `riseSpeed` / `spawnMs` 坡度压陡
（`62 + t*2` → `62 + round(t*2.6)`，`780 - t*8` → `780 - t*10`），
现在也紧到 0.6 秒，且仍落在 `levels188.test.ts` 定的可玩上下界之内
（`riseSpeed ≤ 120`、`spawnMs ≥ 560`）。前 99 关的生成指纹一字未动。

#### 3）`destroy` 仍旧收得干净

本轮有两处动了运行时，都各自复验：

- **`bubble-pop/index.ts` 的 `tide()` 现在会连推两行。**
  改法上刻意让循环体只调 `pushUpRow`（纯函数），
  定时器仍旧全部经 `bag.after(...)`，一处都没绕过口袋。
  复验：连开连关 20 轮，假宿主里一个活口都不剩；
  收摊之后再排一件活儿会当场就地收掉，`alive` 立刻转 `false`。
  顺手把这一处的两个 `as` 断言去掉了（`grid` 本来就是 `number[][]`，不需要转）。
- **`adventure-king/index.ts` 的种子从「每间一摇」改成了「一趟一个」。**
  `runSeed` 是 `mountEndlessCastle` 里的 `const`，随这一趟一起走，
  不进模块作用域、不挂全局，`destroy` 之后自然消失。
  复验：`Disposer` 连收 10 件一把清零，`dispose` 两次不会把同一件事收两遍。
