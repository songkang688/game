### 1.3 修法一：`smartMove` 不再重复计防守

**根因。** 老版本的总分是

```
自家分 × 1.0  +  对手分 × 0.95  −  0.6 × 对手落子后的最佳回应
```

「占掉对手要点」这件事被算了两遍：`0.95` 一遍，`−0.6 × reply` 又一遍
（`reply` 之所以变小，主要就是因为我这一手占掉了对手的最好点）。
等效防守权重 ≈ 1.55、进攻权重只有 1.0 —— 聪明档比普通档（防守 0.9）**更怕事**，
只会拆家不会成家，长局必输。这解释了测试员测到的两件事：85% 的局面它在抄普通档，
剩下 15% 的「自选动作」反而下成了软棋。

**改法。** 防守权重与普通档对齐（`SMART_DEFENSE = 0.9`），多出来的那一层只用来看
「对手的下一手」，不再给防守重复加码。新的聪明档比普通档多会三件事：

1. 自己手里已经有要害点（活四 / 双冲四 / 冲四活三 / 双活三）就直接拍下去 ——
   对手已经握着活四 / 双冲四时抢不过，那种局面交给下面的破杀分支；
2. 三手之内的连续冲四杀（大师看五手、地狱看七手，梯度是有的）；
3. 对手有要害点时，不只会占那个交叉点，也会**拆掉组成它的那条活三** ——
   落完子真的再查一遍对手还有没有要害点，破得掉才走；
4. 平静局面下多算一层：把「这一手会不会把要害点送给对手」当成硬扣分（−250000），
   并按 `SMART_TEMPO = 0.1` 的小权重看一眼对手下一手的最高进攻分（只用来分节奏）。

第 4 条里的 `0.1` 是量出来的：0.05 时聪明档强到反压大师，0.15 起又变回怯懦档（和棋 22/36）。

### 1.4 修法二：`masterMove` 把对手的形看重一档

聪明档改强之后，大师档在 `ai.test.ts` 那条「黑白两边都赢得过聪明档」的老用例上
掉了 3/12（都是执白输）。这不是聪明档改过头，是大师档自己的短板被照出来了：
它手里有算杀（VCF 5 手 / VCT 3 手）和三层前瞻，进攻这一头本来就够用，
真正会输棋的是「对手在别处慢慢做形，它只顾自己长」。

于是把挑点时对手棋型的权重 `0.95 → 1.15`（`MASTER_DEFENSE`），并顺带修了破杀那一段：

- 解法候选（`defenseCandidates`）多收一批「自己这边分数最高的点」——
  一边解杀一边落在要点上最划算，老版本的候选池里只有「对手觉得好的点」；
- 挑法（`pickDefense`）从「按固定顺序试，拿到第一个安全的就走」改成两道筛子：
  先要「对手不再有必胜招」，再要「对手至少没有现成的要害点」，
  同一道筛子里选自己这边分数最高的那个。老版本一个都不安全时直接返回 `tries[0]`，
  那个顺序是拍脑袋定的，等于随手一放。

改完之后大师档不但把聪明档压回去（36-0-0），对简单档执白也从 8 胜 2 负变成 9 胜 1 负。

### 1.5 修法三：`hellMove` 两道口子各堵一道

**口子一 · 破杀（`ai.ts` 老代码 1096–1099 行）。**
老版本对手一有活四 / 双三 / 连续冲四就 `return masterMove(...)`，21% 的中盘局面地狱档**压根不搜索**。
现在改成走 `hellDefend`：解法候选仍旧是大师档那一批（一个都不少，还额外把大师的答案塞进去），
但多了两道地狱档专属的关：

1. 复核用的算杀更深 —— 大师看 `findVcf(opp, 4)`，这里看到 **6 手**，还要求对手没有连续威胁杀；
2. 幸存下来的解法不是「按顺序拿第一个」，而是逐个交给限时深搜打分，挑分最高的。

一个都活不下来、或者预算太紧搜索一层都没算完时仍旧退回大师档的答案，
所以它**不可能比大师档弱**。

**口子二 · 平静局面（老代码 1104–1116 行）。**
`SEARCH_OVERRIDE_MARGIN` 从 **4000 降到 200**。4000 约等于一个活二的价值，
测试员实测 60 个真实中盘局面**一次都没跨过去** —— 深搜白算，两档因此 100% 同步。
200 是「一个五格窗口里多一颗子」的量级，深搜确实说得上话；
同时仍然要求它**严格更好**才改着，改着之后还要过一遍「不许把杀招送给对手」的保险。

配套加了一道 `SEARCH_OVERRIDE_MIN_DEPTH = 4`：预算被压得很紧（比如老用例里的 12ms）时
迭代加深只来得及跑两三层，那种半成品的分数不配改写一手已经过了算杀复核的棋 ——
这时老老实实用大师档的答案。没有这道闸，`地狱 vs 普通 12 局` 那条老用例会因为
「拿半成品搜索结果改着」而掉到 9:3。

margin 也是量出来的：

| margin | 地狱→大师（8 局 ×3） | 地狱→普通（老用例口径） |
| --- | --- | --- |
| 4000（原值） | 4-4-0 / 4-4-0 / 4-4-0 | 10-2-0 |
| 800 | 4-4-0 / 4-4-0 / 4-4-0 | 11-1-0 |
| **200（选定）** | **8-0-0 / 5-3-0 / 6-2-0** | **11-1-0** |
| 100 | 8-0-0 / 8-0-0 / 6-2-0 | 9-3-0 ← 老用例红 |
| 0 | 4-4-0 / 6-2-0 / 4-4-0 | 11-1-0 |

### 3.2 `match-stars`：消除 → 下落 → 补位 三个可观察阶段，无瞬变后门

拿 `domStub.ts` 的虚拟时钟一帧一帧（16ms/帧）走完一次出手的整条时间线，
每帧记段名、飘在半空的方块数、以及关键格子的**视觉行**：

```
段序: swap → boom → fall → land → settle
各段帧数: swap=9 boom=13 fall=16 land=6 settle=8
  ① 消除(boom)  13 帧 ≈ 208ms
  ② 下落(fall)  16 帧 —— 这 16 帧里「幸存块在半空」的帧数 = 16
  ③ 补位(fall)  16 帧 —— 这 16 帧里「新块还在盘外」的帧数 = 16
```

中间态逐帧可见（节选，视觉行[12] 逻辑行是 3、视觉行[0] 逻辑行是 0）：

```
t= 320ms boom  飘空0  视觉行[12]=3.00  视觉行[0]= 0.00
t= 352ms fall  飘空4  视觉行[12]=0.00  视觉行[0]=-3.00   ← 新块从盘外 -3 行开始
t= 416ms fall  飘空4  视觉行[12]=0.56  视觉行[0]=-2.92
t= 480ms fall  飘空4  视觉行[12]=2.09  视觉行[0]=-1.95
t= 544ms fall  飘空4  视觉行[12]=2.96  视觉行[0]=-0.46
t= 592ms fall  飘空4  视觉行[12]=3.00  视觉行[0]=-0.01
```

幸存块从 0.00 一路**浮点滑到** 3.00，不是一帧到位；补位的新块从盘外 −3.00 往里落。
三段各自跨 ≥2 帧 → **不构成瞬变**。

`prefers-reduced-motion` 不另开瞬变分支：

```
常规轨迹: swap → boom → fall → land → settle
降速轨迹: swap → boom → fall → land → settle     一致=true
```

`destroy`：window 监听 0 → 0，残留定时器 0。
