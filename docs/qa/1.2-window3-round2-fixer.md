## 三、【严重·已修】`puff-bros` 两种无尽共用一个成绩位

这是本轮自查挖出来的，此前没人报过。

### 3.1 现象

本款有**两种**无尽，各有各的单位：

- 「♾️ 噗噗不停」记**分**：`endlessScore = cleared*12 + candies*6 + waves*40`，
  随手一趟就是两三百分；
- 「🎈 上升气流」记**米**：一段 20 米，爬得好也就几十米。

两边都读写平台那**同一格** `save` 的 `endlessBest`，而 `recordEndlessBest` 是取 max。
量级差着 4–10 倍，于是：

1. **上升气流再也刷不出新纪录**。孩子玩过一趟噗噗不停（比如 321 分）之后，
   再去爬气流，爬到 80 米，`80 > 321` 不成立 → 判定「没破纪录」，
   还会安慰他「最好成绩 321 米，再来一趟就追上啦」——那是个在这个模式里**永远追不上**的数。
2. **数字被按错误的单位念出来**。321 是分数，上升气流那一格是按「米」渲染的
   （`heightLine()`），于是界面上写着「🏅 最好 321 米」，孩子根本没爬到过那个高度。
3. 模式条上两颗按钮显示的是**同一个数字**：
   「♾️ 噗噗不停 · 最好 321」和「🎈 上升气流 · 最好 321」。

### 3.2 修法

平台每款只给一个无尽成绩位，而那是窗口 1 的文件、不许改，所以只能在本款内部分格：

- 平台那一格留给「噗噗不停」（它是本款主无尽，也是模式条上的主入口），继续记分；
- 「上升气流」改用本款自己的 `CLIMB_BEST_KEY`（`updraft.ts`），继续记米。
  同目录的 `duo-vs-star` 早就用自己的 `localStorage` 键存合作关进度，是本仓成熟做法。
- 两颗按钮各念各的单位：「最好 321 分」/「最好 80 米」。
- 读写都包了 `try/catch`：无痕窗口里 `localStorage` 被禁用时安静地当作还没有纪录，
  不能让存储异常把结算流程搞崩。
- `parseClimbBest` 把坏数据（`null` / 空串 / `"NaN"` / 负数 / `"abc12"`）一律读成 0，
  `serializeClimbBest` 把小数 / 负数 / `NaN` / `Infinity` 规整掉，绝不让 `NaN` 落盘。

### 3.3 用例（+11 条，其中 1 条是把断言错误行为的老用例改对）

`updraft.test.ts` 新增 5 条（键名、读写往返、坏数据、规整、量级对比），
`runtime12.test.ts` 新增 1 条整趟跑通的用例、改写 1 条：

原来那条叫「高度写进 `recordEndlessBest`」，断言是
`expect(...endlessBest).toBeGreaterThanOrEqual(before)`——
这是条**恒真**的弱断言（取 max 决定它永远成立），既没抓住 bug，改完也不会红。
现在它改名为「写进本款自己那一格，不动平台那格」，并且：

- 先往平台那格垫 321 分，再断言上升气流界面上**不出现**「321 米」；
- 断言高度落进了 `CLIMB_BEST_KEY`；
- 断言爬一趟**不会**把平台那 321 分顶掉（`toBe(before)`，从不等式收紧成等式）。

断言条数 7 → 12。新增的那条则完整走一遍「垫分 → 看两颗按钮各念各的 →
爬一趟必是新纪录 → 回菜单两颗按钮仍各念各的」。

## 四、`destroy` 无泄漏：补齐最后一款

第 1 轮我给 4 款补了运行时覆盖。本轮把 19 款的 `destroy` 断言数重新数了一遍，
两个最薄的是 `duo-arena`（4）和 `garden-guard`（6），逐个查下来**一真一假**。

### 4.1 【一般·已补】`duo-arena` 验的是账本，不是接线

`duo-arena/lifecycle.test.ts` 的 4 条用例喂的是**假宿主**，验的是 `createLifecycle`
这个账本本身「挂上去多少、拆下来多少」。账本没问题。

但**没有任何用例真的挂过 `index.ts`**。也就是说「`index.ts` 真的把每一条线都记上了账」
这件事从来没被验证过——只要哪天有人在 `index.ts` 里直接写一句 `window.addEventListener`
绕开 `life.listen`，账本再干净也拦不住，而那 4 条既有用例一条都不会红。

本轮补 `duo-arena/domStub.ts` + `destroy.test.ts`（9 条），真挂一次游戏数 window 上的线：
刚挂载就拆、开擂打一会儿再拆、拆完再敲键 / 跑帧 / 走定时器、退出擂台再拆、
重复 `destroy` 三次、连点三种玩法再连点开擂、暂停幕布开着时拆、按着键不放就拆。

**9 条一次全绿**——说明 `index.ts` 的接线本来就是对的，这是**补覆盖，不是修缺陷**。
但这层保险从今往后才存在。

桩是从 `duo-rush/domStub.ts` 改的，去掉了本款用不到的 `Image` 与裸 `clearTimeout` 兜底，
补了两样本款需要的：`window.requestAnimationFrame` / `cancelAnimationFrame`
（本款帧循环走的是 `window.` 上那一对，不是裸的），
以及选择器的**后代组合符**支持（本款要用 `.dua-clock .t`、`.dua-modes button`）。

### 4.2 `garden-guard` 的 6 条是够的

它的 `destroy` 用例是真挂 `index.ts` 的，验了 rAF 取消、`matchMedia` 监听摘除、
画布摘掉、画布上所有元件监听清零。而本款 `index.ts` **根本不注册**
`window` 监听 / `setTimeout` / `setInterval` / `ResizeObserver`（实测 0 处），
所以它的实际接线面已经被覆盖完了，不需要补。

### 4.3 竞态与抢按（+16 条，`f5754e8`）

顺着 `destroy` 一起补的：`bumper-cars` / `bowling-lane` / `duo-vs-star` / `duo-rush`
各加 4 条抢按用例——连点模式键、连按开打、倒计时中途退出、按着键 `destroy`。
其中 `duo-rush` 那两条**一开始是红的**，但红的原因在测试桩不在玩法：
本款排队用 `window.setTimeout`、取消却用**裸的** `clearTimeout`
（浏览器里这两个本来就是同一个函数，所以线上没毛病；node 里裸的那个够不着桩的队列）。
桩改成「裸 `clearTimeout` 先在桩的队列里找，找不到再交回 node」之后转绿，
这是**桩的保真度问题，不是玩法缺陷**，玩法代码一行没改。

## 五、无尽与难度曲线巡检

### 5.1 覆盖面

### 5.2 【一般·已补断言】`duo-arena` 有两条守擂梯子，只有一条接了线

- `arena12.ts` 的 `defenseAiLevel()`：每 **两** 场升一档；
- `match.ts` 的 `keepSetup()`：每 **一** 场升一档。

真正接进 `index.ts` 的是后者（`arena12` 那边只有 `bestStreak` 被用到），
攻略里写的「守擂一场比一场强」说的也是后者，所以**玩家看到的行为是对的**。
问题是下一个人很可能去调那条没接线的，调完发现游戏里没反应。

本轮补 2 条断言钉住「谁接线、攻略跟谁一致」（前四场就走满四档 = 一场一档，
不是两场一档）。删哪一条要主管拍板，见第六节 L5。

### 5.3 【一般·已补断言】`duo-vs-star/balance12.ts` 是一份没接线的规格

`balance12.ts` 写在 1.2 早期，一口气定了五件事的规格。后来这五件事各自落到了专门的文件里，
本文件只剩第一节还在干活：

| 规格（`balance12.ts`） | 真正接线的实现 | 谁在用 |
| --- | --- | --- |
| 一、循环赛胜率矩阵 | 就是本文件 | 本文件的测试（校验 `roster` 平衡） |
| 二、挣扎窗口 | `knockback.ts` | `battle.ts` → `index.ts` |
| 三、强道具蓄力 | `items.ts` 的 `charge` | `battle.ts` → `index.ts` |
| 四、合作关配合点 | `coop.ts` | `battle.ts` / `index.ts` |
| 五、后段行为化难度 | `ai.ts` + `levels.ts` | `battle.ts` → `index.ts` |

二～六节是**没接线的第二份真相**，而且数值和接线那份并不一致
（挣扎门槛：规格是 `0.72 × 320 = 230.4`，接线的 `knockback.ts` 是元气 ≤ 40 即 **192**；
削减幅度规格是最多 30%，接线的是一次削 55%）。

**玩家现在不会因此出错**——跑的一直是 `knockback.ts` 那份，而且它在
`battle.test.ts` / `knockback.test.ts` 里被验得很透。第一节的循环赛模型是**正当的**
测试用平衡校验工具（同 `monster-crisis/arenaSim.ts`），不算死代码。

本轮补 4 条断言钉住「玩法代码一律不 import 本文件」「接线的挣扎是 `knockback.ts` 那份」
「两份都认的那个 0.4 秒窗口必须一致」「蓄力 / 合作 / 后段行为各有接线实现」。
删哪几节要主管拍板，见第六节 L6。
