### 1. `merge-2048` 的读屏播报会积压 —— 落地

**问题**。第 1 轮我给 `.mg-say` 接了 `aria-live="polite"`，每走一步写一句。
修复员复核时留了个观察点：`polite` 只保证**不打断**当前朗读，它**不会替你合并** ——
玩家连着快滑四下，读屏就排四句，等它念完「第 1 步」，盘面早已经是第 4 步了。
慢的时候没问题，快的时候播报反而变成噪音。

**做法**。加一个 `createSayThrottle(hooks, gap)`：

- **首句立刻写**（慢慢走的玩家一句不少，第 1 轮的既有断言原样通过）；
- 窗口（`SAY_THROTTLE_MS = 900`）之内再来的只**攒最后一句**，到点补写；
- 结论（达成 / 卡死 / 步数用完）走 `urgent`：立刻写，并把攒着的「第几步」丢掉，
  免得玩家已经赢了、读屏还在念第 7 步；
- **一块盘一个闸**。双人同屏是两块盘各自算窗口，朵朵走一步、星星走一步不会互相排队
  （既有的「双人播报带上是谁走的」那条用例正是靠这一点保持绿的）；
- `destroy()` 里 `cancel()`：攒着的那一句在卸载后不会再写。

时钟、定时器全部可注入，所以节流本身是纯逻辑，能用注入时钟逐条钉死。

**验证（会红的回归测试）**。把 `sayers[i].polite(...)` 改回 `say.textContent = ...`
（即第 1 轮的写法），`npx vitest run src/games/merge-2048/index.test.ts` →
**2 failed | 64 passed**，红的正是「连着快滑只播最后一句」与「攒着的那句在 destroy
之后不会再冒出来」。恢复后 66/66。

**没碰的**：合成规则、动画时长、`aria-live` 的 politeness 级别、可见文案一个字都没动。

### 4 / 5. 再铺两款读屏播报：`weiqi-garden` 与 `sudoku-petal` —— 落地

第 1 轮只在 `merge-2048` 上跑通了做法（第 11 条说好「一轮一到两款慢慢铺」），
本轮按这个节奏铺了两款。**一次只改这两款，没有横扫 12 款文案。**

**`weiqi-garden`**。棋盘是画布，读屏只听得到「十九路棋盘」这一句静态 `aria-label`，
之后落哪儿、提了几颗、该谁下全靠看芯片。

- `.wq-msg` 变成 `role="status"` / `aria-live="polite"` / `aria-atomic="true"`；
- 新增看不见的 `.wq-say`（1px 收起，不是 `display:none`，那样读屏也读不到）：
  自由对局播「第几手、轮到谁、两边各提了多少」，数一数阶段改播「已标死几颗」，
  闯关播「第几手、还剩几手」，这一步的提示接在后面；
- **同一句不重写**。闯关有一个每秒 `refresh()` 的倒计时：秒数在变，盘面没变。
  不加这道闸，读屏会**每秒把同一句再念一遍**。
- 播报文本抽成 `saySentence` / `matchSay` / `puzzleSay` 三个纯函数。

**这一条也有会红的回归证据**：去掉「同一句不重写」的守卫，
「倒计时每秒重画一次界面，读屏那一句不跟着重复念」立刻变红（假 `setInterval` 推 3 秒，
断言时间芯片确实从 120 走到了 117、而 live 区一个字都没重写）。

**`sudoku-petal`**。格子本来就有逐格 `aria-label`（这一点第 1 轮做得不错），
缺的是「刚才那一手成没成、还剩多少朵、还能错几次」。

- `.sp-msg` 与桌面的 `.sp-pause` 变成 `role="status"` 的 live 区；
- 新增看不见的 `.sp-say`：种对了播「第几行第几列种下几，还剩多少朵」，
  种错了播「还能改几次」（不判负的局不吓唬人），擦掉、种满、收场各一句；
- **假人那块盘一句不播**（`opts.who` 为空就直接返回），否则竞速时读屏会被假人刷屏；
- 文本抽成 `cellSay` / `fillSay` / `wrongSay` / `clearSay` / `doneSay` 五个纯函数。

**故意没做的一件事**：光挪光标不播报。方向键移动很快，一路按过去会像
`merge-2048` 那样积压；要么按第 1 条那样上节流，要么改成给格子做焦点管理
（格子本来就是 `<button>`，`focus()` 一下读屏自己会念 `aria-label`，可能比 live 区更合适）。
两条路都需要先想清楚再动，留给第 3 轮，见第四节。

## 三、试了但**停手**的一条：`view25d` 的透视数学复用

任务里点名要「让窗口 1 里仍各抄一份透视数学的游戏改为复用共享 `project()`」。
我先量了一遍，结论是：**窗口 1 的 12 款里，一款都没有透视数学可复用。**

取证（`rg "Math\.tan|cameraZ|horizon|地平线|fov|视场角"`）：

| 位置 | 命中 |
| --- | --- |
| 12 款窗口 1 游戏 | 0（唯一一条 `snake-royale/ai.ts:162` 的 `horizon` 是假人**预判时长**，不是地平线） |
| `src/engine/view25d.ts` | 共享的那一份 |
| `src/games/duo-rush/view25d.ts`、`src/games/rainbow-run/view3d.ts` | 1.1 的两份原件 |

`orb-arena` / `snake-royale` 用的 `cam` 是**平面平移 ＋ 缩放**的 2D 相机
（`toX = w/2 + (x - cam.x) * cam.zoom`），没有深度概念；共享模块的 `flat` 档
是「缩放恒为 1、世界 x 直接居中」，硬套上去等于把镜头缩放整个吃掉 —— **这会改手感**，
按纪律停手。真正还各抄一份的是 `duo-rush` 与 `rainbow-run`，**都不在窗口 1 的目录清单里**
（`rainbow-run` 还是窗口 2 的点名项），越界去改是事故。

所以这一条我只做了力所能及、且不碰手感的那一半：**把 `project()` 等整套透视 API
从 `engine/index.ts` 出口**（第二条）。收敛三份透视需要跨窗口排期，建议由主管统一安排，
不要在游戏窗口里动。
