## 二、盲区补课：棋牌/数字盘面「少而精 + 精 2D」密度基准

> 学习口径同 r1：只记文字结论，不下载、不截图入库、不描摹任何具体造型。本节是对 r1 密度基准表的**题材向修订**——r1 按「款」给了数字，本节把「棋牌/数字盘面」这一类题材的共性规律写透。**不学 2.5D/透视，也不把他窗题材（跑酷视差、塔防光影）的密度结论搬进本窗——那些结论对信息盘面无效且违反精 2D 红线。**

### 2.1 「少而精」在本窗的精确含义

1. **盘面本身就是装饰**。棋盘格纹、数字块色阶、牌背印章——信息层自带的图案密度已经很高，装饰预算的大头被盘面吃掉。所以棋牌/数字盘面的「满」来得比动作题材早得多：背景静层 ≤2、盘外静饰 ≤3 件、同屏强动效 ≤1 条，就是这类题材的舒适上限（对照：fruit-stack 这种落体题材可以到 3 层 / 6 件 / 5 通道）。本窗 9 款读码复测全部在上限内，**第 2 轮没有任何一条「往画面里加东西」的建议**。
2. **减法的优先级是固定的**：要给画面减负时，先减动效通道（同屏两条强动效必砍一条）→ 再减盘外装饰 → 最后才考虑盘内；而**盘内信息记号永远不减**——军衔条、战力点、种子点、星级角标这类「数量×形状」记号是给不认字/色弱孩子的通道，宁可素也不能拆。
3. **头部同题材产品的共同做法**（结论文字）：棋盘类头部作品的装饰几乎全部押在「盘框」上（木框、描边、四角件），盘内保持零装饰；数字盘（2048/数独/扫雷）则押在「格底色的极浅纹理」上，纹理对比度低到灰度化后消失。两者的共同点是：**装饰只出现在信息层的边界外**。本窗的 merge-2048 木框钉角、pool-stars 钻石钉、chess-garden 篱笆花盆、sudoku-petal 田埂木框全部符合这条，无需再动。

### 2.2 「精 2D」可读性三定律（为什么这类题材禁透视，写透）

1. **俯视正投影是盘面信息的唯一无损投影**。棋盘的每一格承载等量信息，透视/等距投影会让远格面积小于近格——在 360px 视口、格宽只有 36–44px 的前提下，远排格子的记号（军衔条、战力点）会先于一切被挤掉。头部棋牌产品即使底层是 3D 渲染，「棋盘平面」也永远正对相机；本库直接精 2D，是同一结论的零成本实现。
2. **2.5D 把「棋子高度”变成「遮挡邻格」**。斜投影下棋子有了立起来的身体，就必然盖住身后那格的落点提示与记号。8×8（chess/dark-chess）、12×5（junqi）盘面上任何遮挡都是信息事故。体积感的正确来源是**两笔以内的层叠明暗**：chess-garden 的 `duoTone`（顶部内缩亮层）、dark-chess 的三停叠色牌背就是范式——渐变等效、零透视、零遮挡。
3. **文字通道存在的盘面必须正投影**。本窗 5 款以汉字/数字为第一信息层（merge-2048、sudoku-petal、junqi-camp、dark-chess、mine-garden 数字）。16px 上下的字形一旦倾斜，笔画粘连立刻掉可读性；dark-chess 窄屏「收点数留汉字」的取舍（≤400px 收起 `g.dcd`）正是「文字通道优先」的正确执行。
4. 推论——**给 C 档的一票否决线**：本窗任何统一化/修复建议若引入 `perspective` / `rotate3d` / `matrix3d` / `translateZ` / three.js，一律不做。A 档 r2 已给 sudoku-petal 与 merge-2048 上了「零透视关键字」机器化契约，建议第 3 轮扩到全部 9 款（用例只增不减，成本每款 1 例）。

### 2.3 16px 剪影经验的本轮增量

r1 三句话（轮廓优先 / 双通道 / 粉彩克制）经 C 档实践后补两条增量结论：

- **角标的落点比造型重要**：junqi 角标放左下（右下被落点绿点占用）证明——第二通道记号必须先盘点该格四角已有的「状态占位」（选中框、落点点、光标框），空角才是落点。给 C 档后续加角标类记号时先画「四角占用表」。
- **「数量可数」的记号在 11px 见方就够用**：`jq-mark` 11×11px、dark-chess 战力点 r=1.9px 实测都活到了 16px 灰度化。比「放大记号」更要紧的是记号周围留 ≥1.5px 的静空，挤着汉字就两败俱伤。
